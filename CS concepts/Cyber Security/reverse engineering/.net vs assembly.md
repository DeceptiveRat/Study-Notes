Yes, you're absolutely right — and you've touched on an important distinction in how different programming languages compile code.

### Why .NET decompilers are so accurate:
C# (and other .NET languages like VB.NET or F#) compiles to **Intermediate Language (IL)**, not directly to native machine code. IL is a **higher-level, structured bytecode**, which retains a lot of the original program structure — including class names, method names, and even some comments (if debug info is preserved).

- Tools like **dnSpy**, **ILSpy**, and **dotPeek** can take this IL and reconstruct code that is *very close* to the original C# source.
- This is possible because the compiled IL code is **designed to be run by the .NET runtime (CLR)**, and it's much more "readable" than native assembly.

### Why reversing native binaries is harder:
In contrast, when C/C++ code is compiled, it's turned into **native machine code**, which:
- Strips away most high-level constructs.
- Loses variable names, comments, and structure.
- Is optimized by the compiler (e.g., inlining, loop unrolling), making reverse engineering even harder.

So when you reverse native code, you often only get disassembly or poorly reconstructed pseudocode (e.g., from IDA Pro or Ghidra) that **requires interpretation** and analysis.

### So yes, C# is easier to reverse:
Because of this architecture, **.NET applications are significantly easier to reverse engineer** than native applications. This is a well-known tradeoff with managed languages like C# and Java.

### Mitigation:
.NET developers often use **obfuscators** (e.g., ConfuserEx, Dotfuscator, SmartAssembly) to make reverse engineering harder by:
- Renaming variables and methods to meaningless names.
- Encrypting or encoding IL code.
- Injecting anti-debugging or anti-decompiling tricks.
